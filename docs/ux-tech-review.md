# UX 与技术可行性评估（ux-tech-review）

## 评估方法说明

本评估基于现有规范文档（`docs/`、`remediate-foundation/`）的静态文本分析，未执行真实浏览器、移动设备或辅助技术实测。凡涉及真实设备/浏览器交互、第三方组件库兼容性、Lighthouse 实际跑分等依赖运行时验证的项，统一标注"待真机验证"。文档结论仅作为实现前的可行性研判，最终落地以真机验证为准。

## 1. 移动端界面设计

- **评估项**：移动端单列布局、输入/计算/结果三层结构、复制分享能力
- **设计要求原文引用**：「顶部面包屑 + 工具名 → 中部输入 + 计算 → 底部结果 + 解释 + FAQ + 相关工具」；输入字段使用 `inputmode="decimal"` 与单位后置；错误采用行内红字 + 按钮置灰（而非整页 alert）；结果展示主 32px / 次 14–16px，并支持复制/分享
- **开发难度**：低。Astro 静态组件 + 少量客户端 hydrate 即可覆盖
- **技术栈匹配度**：高。Astro 默认输出静态 HTML，与移动端 SEO/性能目标契合；复制/分享走 Web Share API + 剪贴板降级
- **技术限制**：
  - 微信内置浏览器对 Web Share API 支持有限（待真机验证）
  - 主结果 32px 在 320px 视口下需验证是否触发横向溢出
- **裁决结论**：**可实现**

---

## 2. 表单元素设计

- **评估项**：原生表单控件选型、单位后置、跨端一致性
- **设计要求原文引用**：使用原生 `<input type="date">` 避免自定义日历；使用原生 `<select>`；单位后置于输入框尾部；需验证 iOS Safari 与 Android Chrome 范围输入（`type="range"`）表现差异
- **开发难度**：低～中。原生控件成本低，但单位后置需自行组合 `flex` 布局
- **技术栈匹配度**：高。原生控件与 Astro 静态输出兼容良好
- **技术限制**：
  - iOS Safari 对 `<input type="date">` 的展示与系统区域设置强相关（待真机验证）
  - 单位后置在 RTL 语言下需额外处理
- **裁决结论**：**可实现**

---

## 3. 可访问性标准

- **评估项**：语义化、键盘可达、辅助技术提示、视觉对比
- **设计要求原文引用**：语义化 HTML；`<label>` 关联所有控件；动态结果区使用 `aria-live="polite"`；错误态使用 `aria-invalid` + `aria-describedby`；`focus ring` 必须可见；文本对比度 ≥ 4.5:1
- **开发难度**：中。需要逐控件补齐 ARIA 属性，并建立焦点顺序约定
- **技术栈匹配度**：高。纯前端属性，与 Astro 无冲突
- **技术限制**：
  - Lighthouse 分数不等同于 WCAG 合规，需人工 + 屏幕阅读器（VoiceOver / TalkBack）补充验证（待真机验证）
  - `aria-live="polite"` 在部分安卓浏览器的中文 TTS 引擎下朗读时机会延迟
- **裁决结论**：**可实现（但 Lighthouse 分数 ≠ WCAG 合规，需人工验证补充）**

---

## 4. 广告布局方案

- **评估项**：广告槽位预留、CLS 控制、降级路径、同意管理对 LCP 的影响
- **设计要求原文引用**：固定尺寸预留容器以避免 CLS；广告失败需有降级路径；同意管理触发时机需与 LCP ≤ 2.5s 相容
- **开发难度**：中。需在 Astro 组件中预设占位容器与失败回退
- **技术栈匹配度**：中。需引入第三方广告脚本，需评估其与 Astro 静态化的协作方式（脚本注入时机、懒加载策略）
- **技术限制**：
  - 广告脚本异步性可能拉长 LCP，需通过 `requestIdleCallback` / `defer` 控制
  - 同意管理（CMP）弹窗若同步阻塞渲染，将直接劣化 LCP
  - 第三方广告 SDK 在微信/小程序 WebView 内的兼容性需真机验证
- **裁决结论**：**可实现（但需依赖前置条件解锁：广告供应商选型、CMP 选型、Astro 集成方式敲定）**

## 5. 页面结构规划

- **评估项**：将 `remediate-foundation` Task 8.1 的页面骨架落地到 Astro 组件层级
- **设计要求原文引用**：页面骨架顺序为「面包屑 → H1 → 输入区 → 计算/重置 → 结果区 → 说明 → FAQ → 相关工具 → 广告位 A」
- **开发难度**：低。直接映射 Astro 组件树即可
- **技术栈匹配度**：高。完全契合 Astro 的静态组件化模型
- **技术限制**：
  - 相关工具模块在 MVP 阶段如缺乏数据，需以空状态降级
  - 广告位 A 的占位需与"广告布局方案"联动落地
- **裁决结论**：**可实现**

---

## 6. 组件状态定义

- **评估项**：组件状态机的显式定义（覆盖空/加载/错误/禁用/聚焦/有效等态）
- **设计要求原文引用**：当前规范**缺失**以下状态机定义——输入框 6 态、按钮 4 态、结果区 4 态（含"待重算"）、广告容器 4 态（加载/成功/失败/空）
- **开发难度**：中。需新增状态机文档与组件契约
- **技术栈匹配度**：高。属于文档与组件层工作，与 Astro 无技术冲突
- **技术限制**：
  - 状态枚举需与"结果展示主 32px / 次 14–16px"等既有规范保持术语一致
  - "待重算"态需明确触发时机（输入变更后但尚未重新计算）
- **裁决结论**：**需补齐**（→ 写入 `docs/design-system.md`，对应 `remediate-foundation` Task 9）
- **降级方案**：MVP 阶段先在组件内注释临时状态机，文档化工作并行推进；不允许在无状态机定义的情况下进入"待验收"列

---

## 7. 响应式设计标注

- **评估项**：断点定义、跨视口一致性
- **设计要求原文引用**：当前规范**未给出**断点定义与各档位的布局/字号/间距规则
- **开发难度**：低（文档补齐）；中（实现 CSS 变量与媒体查询体系）
- **技术栈匹配度**：高。Astro + 原生 CSS / PostCSS 即可承载
- **技术限制**：
  - 320px 视口（iPhone SE 1 代）需作为下限基准
  - 平板（≥768px）与桌面（≥1024px）的版式需区分
- **裁决结论**：**需补齐**（→ 写入 `docs/design-system.md`，对应 `remediate-foundation` Task 9）
- **降级方案**：建议采用三档断点——**320–479（小屏手机）/ 480–1023（大屏手机 + 平板）/ ≥1024（桌面）**；MVP 前必须补齐断点表与字号/间距比例

## 待真机验证条目

以下条目无法仅凭静态文档分析定论，必须在真机/真实浏览器环境中验证后方可作为最终验收依据：

1. iOS Safari 软键盘弹出后，与原吸底按钮布局（已改为常规文档流）的实际交互是否仍存在遮挡/跳动问题
2. 微信内置浏览器对 Web Share API 的支持情况，及降级到 `navigator.clipboard` 的成功率
3. 滑块控件（已从 MVP 移除）在 iOS Safari / Android Chrome 上的触控手感与精度可控性，作为后续版本回归评估参考
4. `<input type="date">` 在 iOS Safari 不同系统语言/区域设置下的展示一致性
5. Android TalkBack / iOS VoiceOver 对 `aria-live="polite"` 结果区的中文朗读时机与完整性
6. 广告脚本与同意管理（CMP）在真实 LCP 测量下的影响（需 Lighthouse + 实地网络条件）
7. 主结果 32px 字号在 320px 最小视口宽度下是否触发横向溢出
8. 第三方广告 SDK 在微信/小程序 WebView 与各国产浏览器内核下的兼容性与降级表现
