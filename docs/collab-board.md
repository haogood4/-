# 协作看板与沟通规范（collab-board）

本文档定义计算器网站开发项目内部的协作看板结构、任务命名、沟通节奏、负载保护与文档管理规则，适用于项目全体成员（含产品、设计、前端、后端、测试、运维）。

---

## 1. 看板定义

采用 6 列看板进行任务流转。各列含义如下：

| 状态 | 进入条件 | 退出条件 | 默认负责人 | 进入该列需满足的额外约束 |
| --- | --- | --- | --- | --- |
| 待梳理 | 已识别需求或问题，尚未澄清范围 | 产品（PM 角色）已澄清范围并形成 SubTask | 产品（PM 角色） | 必须关联到至少一个计算器或模块；输出 1 句话目标 |
| 待开发 | SubTask 已拆分清楚，含验收点 | 开发者接受并开始执行 | 产品（PM 角色）指派开发者 | 必须含验收点与预估工时；至少有 1 条 AC |
| 进行中 | 开发者接受任务并已在本地/分支上动工 | 产出可评审的 PR/Demo 或被阻塞 | 任务的执行开发者 | 进入时即视为占用 1 个"进行中"名额 |
| 待评审 | 已提交 PR 或 Demo，等待评审 | 评审通过，进入验收；或被打回"进行中" | 前端负责人 / 后端负责人 | PR 必须可运行、含自测说明；阻塞不得停留超 1 个工作日 |
| 待验收 | 评审通过，等待 PM/Owner 验收 | 验收通过进入完成；或被打回"进行中" | 产品（PM 角色） | 必须提供验收清单与录屏/截图证据 |
| 完成 | PM/Owner 确认验收通过 | 进入下一周期或归档 | 产品（PM 角色）归档 | 必须填写实际完成时间与 commit 链接 |

## 2. 任务命名规范

所有卡片标题必须严格遵循三段式：`<工具ID或模块> · <动词> · <期望结果>`。

- **工具ID或模块**：使用真实计算器 ID（如 `mortgage-cn`、`bmi`、`salary-tax`、`compound-interest`）或通用模块名（如 `frontend`、`docs`、`infra`）。
- **动词**：推荐使用"添加"、"修复"、"重构"、"迁移"、"梳理"、"评审"等明确动作，避免使用"处理"、"跟进"、"看看"等模糊词。
- **期望结果**：必须可验证、可交付，避免空泛描述。

### 2.1 正例

1. `mortgage-cn · 添加 · 等额本金计算`
2. `salary-tax · 修复 · 个税专项附加扣除为空时的 NaN`
3. `compound-interest · 重构 · 月复利公式抽取为独立工具函数`

### 2.2 反例

1. `改进计算器` —— 反例错在：缺少工具ID或模块，三段式缺前两段；动词"改进"模糊，期望结果无法验证。
2. `处理一下 mortgage 的 bug` —— 反例错在：动词"处理一下"不明确；期望结果没有写出"修好什么"，无法作为验收依据。

## 3. 沟通节奏

### 3.1 日报

- **提交时间**：每日 18:00（Asia/Shanghai）
- **提交对象**：PM 角色（产品）
- **提交方式**：在飞书/看板指定日报位提交，由 PM 审阅
- **字段说明**：

| 字段 | 说明（1 句话） |
| --- | --- |
| 完成 | 列出昨日已流转到"完成"或"待验收"的卡片 ID 与标题 |
| 进行 | 列出当前"进行中"卡片，并标注预计完成时间 |
| 阻塞 | 列出影响任务推进的具体阻塞项及请求支援对象 |
| 待决策 | 列出需要 PM 或 Owner 拍板的事项与推荐方案 |
| 下一动作 | 列出今日明确要推动的 1~3 个动作 |

### 3.2 周报

- **提交时间**：每周五 18:00（Asia/Shanghai）
- **提交对象**：PM 角色（产品）及项目 Owner
- **附加字段**（在日报五字段基础上增加）：

| 字段 | 说明 |
| --- | --- |
| 里程碑 | 本周里程碑达成/偏离情况，与计划对比 |
| 范围变化 | 本周新增、删除或调整范围的卡片列表 |
| 预算消耗 | 本周人力/云资源/广告等预算消耗占比 |
| 质量 | 本周缺陷数、回归缺陷率、PR 评审一次通过率 |
| 流量与广告 | 本周站点流量、广告投放 ROI、关键转化漏斗数据 |

## 4. 负载保护规则

为避免单点过载导致质量下降，对每位员工的"进行中"任务数量进行硬性约束。

### 4.1 触发规则

- 规则：任一员工"进行中"任务数 **≥ 2** 时，其所有"进行中"卡片在看板中标红。
- 标红由看板自动化规则完成，PM 在每日巡检时复核。

### 4.2 如何重排（3 步流程）

1. **步骤 1：盘点当前"进行中"任务清单与剩余工时**
   由 PM 拉取该员工所有"进行中"卡片，逐条核对剩余工时与优先级 P0/P1/P2/P3。

2. **步骤 2：合并同类项**
   同一计算器的多个 SubTask 可合并为一个 PR / 一次提交；同一模块的相近修复可打包评审，减少上下文切换成本。

3. **步骤 3：暂停低优先级任务并标 P3 / 延期，不删除**
   低优先级任务置为"待开发（延期）"并打上 P3 标签，**不得删除**；延期原因与预计重启日期写入卡片描述。

### 4.3 执行与同步

- 触发后由产品（PM 角色）执行重排。
- 执行结果必须同步到看板（更新负责人 / 优先级 / 状态）并写入当日日报的"阻塞"与"下一动作"字段。

## 5. 文档管理规范

### 5.1 front-matter 必填字段

所有 Markdown 文档必须在文件顶部填写 YAML front-matter，包含以下字段：

| 字段 | 含义 |
| --- | --- |
| project | 所属项目标识，固定为 `calculator-site` |
| doc_id | 文档唯一 ID，格式 `目录/文件名`，如 `docs/collab-board` |
| type | 文档类型，如 `sop`、`spec`、`runbook`、`template` |
| domain | 文档领域，如 `governance`、`tech`、`product`、`ops` |
| locale | 语言区域，如 `zh-CN`、`en-US` |
| version | 语义化版本号，如 `v1.0.0` |
| status | 文档状态，如 `draft`、`active`、`deprecated` |
| effective_from | 生效日期，格式 `YYYY-MM-DD` |
| owner | 负责人角色，如 `产品（PM 角色）`、`前端负责人` |
| last_updated | 最后更新日期，格式 `YYYY-MM-DD` |

### 5.2 存放位置

- `knowledge-base/`：**稳定规则**类文档（如技术栈、编码规范、API 契约、术语表），一经发布少有变动。
- `docs/`：**治理层 / 计划 / 模板**类文档（如本协作看板、模板、年度计划、复盘报告）。

### 5.3 命名规范

文件命名采用 `{domain}-{slug}.md` 形式，例如：

- `tech-stack.md`
- `incident-runbook.md`
- `collab-board.md`（本文档，domain=`governance`）
