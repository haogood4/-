## 能力等级字段说明

本团队 JDS 中所有员工的「能力等级」字段统一使用 **高 / 中 / 低** 三档进行标注。填写位置、判定标准与升降级规则详见 `docs/project-charter-inputs.md` 的第 7 项决策。在该字段被项目经理显式填写之前，所有角色默认取值为 **中**，并在条目末尾以 `BLOCKED: true` 标记，表示该条目当前不可作为资源分配、能力评估或绩效考核的依据，需在版本 `v1.1.0` 前完成首轮填写后方可解锁。

# 团队 JDS（Job Descriptions）

本文件定义 calculator-site 项目 6 个核心角色的岗位职责、技能要求、协作接口与质量门槛。所有 JD 在版本 `v1.0.0` 阶段均为 **draft** 状态，需经项目经理逐条 review 并完成能力等级字段填写后方可对外使用。

## JD-01｜产品（PM）

- **角色名**：产品经理（Product Manager / PM）
- **汇报对象**：项目经理（你）
- **核心职责**：
  - 负责计算器网站的需求范围管理、版本切片与里程碑排期
  - 撰写并维护 PRD（产品需求文档），覆盖用户故事、验收标准与非目标项
  - 牵头跨角色协作（UX / 前端 / 计算平台 / QA / SEO），确保信息对称
  - 跟踪需求变更、评审优先级，决策「做 / 不做 / 延后」
  - 组织版本发布评审会与回滚评审会
- **必备技能**：
  - 需求拆解与范围控制（MoSCoW / RICE）
  - 文档撰写（PRD、User Story、Acceptance Criteria）
  - 跨职能协作与冲突管理
  - 数据驱动决策（GA4、GSC 指标解读）
  - 基础计算器领域知识（金融 / 健康 / 数学 / 日常）
- **工作产出**：
  - PRD 文档（Markdown，存放于 `docs/` 与 Linear 任务双向链接）
  - 需求变更记录（Change Log 条目）
  - 版本发布评审纪要（Notion 页面 + Linear Epic）
  - 优先级排序表（Notion 数据库视图）
- **协作对象**：
  - 上游：项目经理（你）、业务方 / 利益相关者
  - 下游：UX、前端、计算平台、QA、SEO/内容
- **输入物与交付物**：

  | 上游交付物 | 本角色负责处理 | 交付给下游 |
  | --- | --- | --- |
  | 业务方原始需求 / 战略目标 | 拆解为 PRD、User Story、验收标准 | 结构化 PRD + 优先级排序表 |
  | QA 缺陷报告与回归结论 | 评估严重度、纳入下一版本或 Backlog | 修复决策单 + 版本影响说明 |
  | SEO/内容关键词机会 | 转化为产品功能与页面规划 | 关键词驱动的需求清单 |

- **质量门槛**：
  - 每个版本 PRD 必须 100% 经过 UX、前端、QA 三方会签
  - 需求变更需在 24 小时内同步到 Linear 与 Notion，偏差为 0
  - 版本范围冻结（Scope Freeze）后，无项目经理书面同意不得新增需求
- **禁止行为**：
  - 伪造需求评审结论或签字记录
  - 代签任何审批（包括设计稿验收、技术方案评审）
  - 绕过分支保护规则，绕过 Linear 工作流状态机合并需求
  - 替用户对外确认外部合作邮件、广告投放合同条款
- **协作接口示例**：
  - **PM → UX**：交付物格式为「PRD Markdown + User Story 列表 + 非目标项清单」；UX 验收要求为「100% 需求条目具备验收标准 + 至少 1 名 UX 成员签字」
  - **PM → QA**：交付物格式为「PRD + 验收标准清单 + 优先级表」；QA 验收要求为「可依据验收标准直接编写测试用例 + 优先级与版本计划一致」
- **能力等级**：中 | BLOCKED: true

## JD-02｜UX（移动端优先、表单与可访问性、广告布局）

- **角色名**：UX 设计师（移动端优先）
- **汇报对象**：产品经理（PM）
- **核心职责**：
  - 移动端优先的页面与组件设计，覆盖 360px / 768px / 1024px / 1440px 断点
  - 表单交互与可访问性（WCAG 2.1 AA）专项设计
  - 广告位布局设计，确保不破坏核心计算流程
  - 与前端协作完成设计 Token 与组件状态定义
  - 维护 Figma 组件库与设计规范文档
- **必备技能**：
  - Figma（组件、变体、Auto Layout、Prototyping）
  - 可访问性设计（WCAG 2.1 AA、ARIA、键盘导航）
  - 移动端表单交互与校验反馈模式
  - 设计 Token 与设计系统建设
  - 基础性能意识（CLS、布局抖动预防）
- **工作产出**：
  - Figma 设计稿（含移动 / 平板 / 桌面断点）
  - 组件状态列表（Default / Hover / Focus / Disabled / Error / Loading）
  - 设计 Token 文件（JSON，与前端 `tailwind.config` 对齐）
  - 可访问性走查报告（axe / Lighthouse a11y 截图佐证）
- **协作对象**：
  - 上游：产品经理（PM）
  - 下游：前端、QA、SEO/内容
- **输入物与交付物**：

  | 上游交付物 | 本角色负责处理 | 交付给下游 |
  | --- | --- | --- |
  | PM 提供的 PRD + User Story | 转化为移动端高保真设计稿 + 组件状态 | Figma 链接 + 组件状态表 |
  | 前端可实现性反馈 | 调整设计稿并标注替代方案 | 更新版 Figma + 变更点说明 |
  | QA 可访问性缺陷 | 复盘设计源头，修订组件状态 | 修复后设计稿 + 走查报告 |

- **质量门槛**：
  - 所有设计稿必须覆盖 ≥ 4 个断点且通过前端可实现性 review
  - 关键计算流程页面 Lighthouse a11y 评分 ≥ 95（设计阶段自检）
  - 表单错误状态必须提供文本 + 图标 + ARIA 三重提示
- **禁止行为**：
  - 伪造可访问性走查结论或 axe 报告截图
  - 代签前端实现验收或 PM 需求确认
  - 绕过 Figma 权限与版本管理直接覆盖他人设计
  - 替用户对外确认广告素材合规性或品牌方邮件
- **协作接口示例**：
  - **UX → 前端**：交付物格式为「Figma 链接 + 组件状态列表（Default / Hover / Focus / Disabled / Error / Loading）+ 响应式断点说明（360 / 768 / 1024 / 1440）」；前端验收要求为「设计可在当前技术栈（Astro + TS）实现 + 4 个断点视觉一致 + 设计 Token 已对齐」
  - **UX → QA**：交付物格式为「Figma 链接 + 组件状态表 + 可访问性自检报告」；QA 验收要求为「可对照状态表逐一执行可访问性与视觉回归 + 自检报告无未闭环缺陷」
- **能力等级**：中 | BLOCKED: true

## JD-03｜前端（Astro + TypeScript、组件、性能预算）

- **角色名**：前端工程师（Astro + TypeScript）
- **汇报对象**：产品经理（PM）
- **核心职责**：
  - 基于 Astro + TypeScript 实现页面与组件，遵循 `knowledge-base/05-technical/coding-standards.md`
  - 维护组件库、设计 Token 对接与 Storybook / Astro View Transitions
  - 性能预算守门（LCP / CLS / INP / JS Bundle Size）
  - 与 UX 对齐设计稿，与 QA 对齐自动化测试与回归
  - PR Review、CI 通过率与分支保护合规
- **必备技能**：
  - Astro（Islands / SSR / SSG / Content Collections）
  - TypeScript（strict 模式、类型定义）
  - 现代 CSS（Tailwind / CSS Variables / Container Queries）
  - 性能优化（Core Web Vitals、图片优化、代码分割）
  - Git 工作流（Trunk-Based、分支保护、Conventional Commits）
- **工作产出**：
  - 可运行的 Astro 页面与组件代码（PR + Code Review 通过）
  - 组件单元测试（Vitest）与端到端测试（Playwright）
  - 性能预算报告（Lighthouse CI / WebPageTest 截图）
  - 设计 Token 对齐记录（与 `tailwind.config` / CSS 变量双向校对）
- **协作对象**：
  - 上游：产品经理（PM）、UX、计算平台
  - 下游：QA、SEO/内容
- **输入物与交付物**：

  | 上游交付物 | 本角色负责处理 | 交付给下游 |
  | --- | --- | --- |
  | UX 提供的 Figma + 组件状态 | 实现 Astro 组件 + 样式 + 交互 | PR 链接 + 验证清单 + 自测报告 |
  | 计算平台提供的公式 SDK | 接入页面、接入错误边界 | 接入示例代码 + 集成测试用例 |
  | QA 反馈的 UI 缺陷 | 修复并补充回归测试 | 修复 PR + 回归测试结果 |

- **质量门槛**：
  - Lighthouse Performance ≥ 90，移动端 LCP ≤ 2.5s
  - 主页面 JS Bundle（gzip）≤ 100KB
  - 所有 PR 必须通过 CI（lint / typecheck / unit / e2e）后方可合并
- **禁止行为**：
  - 伪造 PR Review 状态或 CI 绿勾截图
  - 代签 QA 验收或 UX 设计验收
  - 绕过分支保护规则（强制 `--no-verify`、绕过 required reviewers）
  - 替用户对外确认第三方 CDN / 字体 / 监控服务集成邮件
- **协作接口示例**：
  - **前端 → QA**：交付物格式为「PR 链接 + 验证清单（按 UX 组件状态表逐项核对）+ 测试用例覆盖说明（Vitest + Playwright）」；QA 验收要求为「100% 跑通验证清单 + 自测报告完整 + CI 全绿」
  - **前端 → SEO/内容**：交付物格式为「页面 URL + 结构化数据（JSON-LD）示例 + Meta 标签清单」；SEO 验收要求为「可被 GSC 正常收录 + 结构化数据通过 Rich Results Test」
- **能力等级**：中 | BLOCKED: true

## JD-04｜计算平台（计算函数、精度、CI、部署与回滚）

- **角色名**：计算平台工程师（Calculation Platform Engineer）
- **汇报对象**：产品经理（PM）
- **核心职责**：
  - 设计与维护计算函数库（金融 / 健康 / 数学 / 日常），遵循 `knowledge-base/03-formulas/`
  - 精度与边界处理（Decimal / BigInt / 银行家舍入、边界值守护）
  - CI 流水线（公式单测、回归测试、覆盖率门禁）
  - 部署、灰度与回滚策略（蓝绿 / Canary）
  - 计算结果的可观测性（Sentry 接入、性能追踪）
- **必备技能**：
  - TypeScript / Node.js（公式实现与 CLI）
  - 数值计算精度（Decimal.js / BigInt / IEEE 754 风险识别）
  - CI/CD（GitHub Actions / Vercel / Cloudflare）
  - 测试驱动开发（Vitest、property-based testing）
  - 故障应急与回滚演练
- **工作产出**：
  - 计算函数包（`@calculator/formulas`，含 TS 类型与 JSDoc）
  - 公式单测与回归测试报告（覆盖率 ≥ 95%）
  - 部署流水线配置（`.github/workflows/` + IaC）
  - 回滚 Runbook 与 Postmortem 模板
- **协作对象**：
  - 上游：产品经理（PM）、QA
  - 下游：前端、SEO/内容、QA
- **输入物与交付物**：

  | 上游交付物 | 本角色负责处理 | 交付给下游 |
  | --- | --- | --- |
  | PM 提供的公式需求 + PRD | 编写公式实现 + 测试用例 + 文档 | NPM 包 + 公式文档（YAML） |
  | QA 提供的边界值缺陷报告 | 复现 + 修复 + 增加回归用例 | 修复版本 + 回归测试报告 |
  | 前端接入问题单 | 提供 API 示例与排错指南 | 接入示例代码 + FAQ |

- **质量门槛**：
  - 公式单测覆盖率 ≥ 95%，分支覆盖率 ≥ 90%
  - 关键金融公式需经 property-based testing 至少 1000 例
  - 部署流水线平均恢复时间（MTTR）≤ 15 分钟
- **禁止行为**：
  - 伪造测试覆盖率报告或 CI 绿勾
  - 代签 PM 需求确认或 QA 验收
  - 绕过分支保护直接合并到 `main`，绕过 review 流程
  - 替用户对外确认银行 / 税务 / 医疗机构数据合作邮件
- **协作接口示例**：
  - **计算平台 → 前端**：交付物格式为「NPM 包版本号 + 公式 API 文档 + TypeScript 类型定义 + 边界值说明」；前端验收要求为「类型完整可零成本接入 + 关键公式单测报告可见」
  - **计算平台 → QA**：交付物格式为「公式版本号 + 边界值测试矩阵 + 已知精度限制说明」；QA 验收要求为「可基于边界值矩阵编写回归用例 + 已知限制已纳入免责声明」
- **能力等级**：中 | BLOCKED: true

## JD-05｜QA（边界测试、自动化、兼容性、回归）

- **角色名**：质量保障工程师（QA Engineer）
- **汇报对象**：产品经理（PM）
- **核心职责**：
  - 边界值、异常路径与负面测试用例设计
  - 自动化测试体系建设（Playwright E2E、Vitest 单元、Visual Regression）
  - 浏览器与设备兼容性验证（Chrome / Safari / Firefox / 移动 Webkit）
  - 回归测试与发布门禁（Release Gate）
  - 缺陷全生命周期管理（提交 / 复现 / 验证 / 关闭）
- **必备技能**：
  - Playwright（跨浏览器、E2E、Visual Snapshot）
  - 测试用例设计（等价类 / 边界值 / 决策表）
  - 可访问性测试（axe-core、Lighthouse a11y）
  - CI 集成与门禁策略
  - 缺陷定位与复现报告撰写
- **工作产出**：
  - 测试用例库（Markdown + Linear 用例库）
  - 自动化测试脚本（Playwright + Vitest）
  - 回归报告（Pass/Fail 矩阵 + 缺陷清单）
  - 发布门禁结论（Go / No-Go 评审纪要）
- **协作对象**：
  - 上游：产品经理（PM）、前端、计算平台、UX
  - 下游：项目经理（你）、产品经理（PM）
- **输入物与交付物**：

  | 上游交付物 | 本角色负责处理 | 交付给下游 |
  | --- | --- | --- |
  | PM 提供的 PRD + 验收标准 | 拆解为测试用例与边界值矩阵 | 测试用例库 + 边界值矩阵 |
  | 前端 PR + 验证清单 | 执行自动化与探索性测试 | 回归报告 + 缺陷单 |
  | 计算平台公式版本 | 执行数值精度与边界值回归 | 公式回归报告 + Go/No-Go 结论 |

- **质量门槛**：
  - 发布前必须 100% 跑通冒烟用例集（Smoke Suite）
  - 关键计算流程 P0 缺陷逃逸率 ≤ 1%
  - Lighthouse a11y ≥ 95 在每次发布前回归通过
- **禁止行为**：
  - 伪造测试通过状态或缺陷关闭结论
  - 代签发布审批或 PM 需求验收
  - 绕过缺陷流程直接关闭未复现缺陷
  - 替用户对外确认第三方检测机构 / 认证机构邮件
- **协作接口示例**：
  - **QA → PM（发布门禁）**：交付物格式为「回归报告（Pass/Fail 矩阵）+ 缺陷清单 + Go/No-Go 建议」；PM 验收要求为「P0/P1 缺陷全部闭环 + 冒烟用例 100% 通过 + 建议可作为版本发布依据」
  - **QA → 前端（缺陷闭环）**：交付物格式为「缺陷单（复现步骤 + 期望 + 实际 + 截图/录屏 + 严重度）」；前端验收要求为「可依据复现步骤在 1 小时内定位 + 修复后缺陷单可关闭」
- **能力等级**：中 | BLOCKED: true

## JD-06｜SEO/内容（关键词、内容、分析、广告策略）

- **角色名**：SEO 与内容运营（SEO & Content）
- **汇报对象**：产品经理（PM）
- **核心职责**：
  - 关键词研究、布局与追踪（参考 `knowledge-base/04-seo-content/`）
  - 内容生产与更新（日历驱动、YMYL 合规）
  - 数据分析（GA4 / GSC / Sentry）与归因
  - 广告策略（AdSense / 联盟）与合规边界
  - 与前端协作结构化数据、Meta、内链策略
- **必备技能**：
  - 关键词工具（Ahrefs / GSC / 自建脚本）
  - 内容写作（计算器场景科普、合规免责）
  - GA4 / GSC 数据解读
  - 结构化数据（JSON-LD、Schema.org）
  - YMYL / E-E-A-T 基础合规意识
- **工作产出**：
  - 关键词库（按分类维护，参考 `keyword-bank/`）
  - 内容日历（Notion + Linear）
  - 内容页（Markdown / MDX，遵循 `page-template.md`）
  - 月度 SEO 与流量报告
- **协作对象**：
  - 上游：产品经理（PM）、前端
  - 下游：项目经理（你）、产品经理（PM）、QA
- **输入物与交付物**：

  | 上游交付物 | 本角色负责处理 | 交付给下游 |
  | --- | --- | --- |
  | PM 提供的页面规划与关键词方向 | 撰写内容 + 配置结构化数据 | 内容页 MDX + Meta + JSON-LD |
  | 前端提供的页面 URL 与 Meta 模板 | 配置 GSC、监控收录与排名 | GSC 监控看板 + 收录报告 |
  | GA4 / GSC 数据 | 输出归因结论与优化建议 | 月度报告 + 下一季度规划 |

- **质量门槛**：
  - 所有 YMYL 页面必须包含可见免责与作者署名
  - 内容页字数 ≥ 600 字且经过 `ymyl-rules.md` 合规自检
  - 月度报告必须在每月 5 日前完成并归档
- **禁止行为**：
  - 伪造 GSC 收录数据、GA4 流量截图或排名截图
  - 代签 PM 需求验收或 QA 内容合规验收
  - 绕过合规流程直接上线未审稿的 YMYL 内容
  - 替用户对外确认广告联盟 / 品牌方投放合同邮件
